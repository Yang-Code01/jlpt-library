01这次更新改了什么

主线被定型了。以前是一批各自独立的技能，现在 ask-matt（路由器）把 90% 的工作都指向同一条路径：

grill-with-docs→ to-spec→ to-tickets→ implement / implement-spec→ code-review→ pr→ retro

本次更新的三个重点技能，正好是这条链上最后、也是最缺的三段：怎么把工作合并进去（implement-spec）、怎么把 PR 讲清楚（pr）、怎么让下次更顺（retro）。

一句话概括每个重点

  • pr：规定 PR 描述的形状——最小可视化 + 前后对比证据 + 风险判定。只管 body，不开 PR。
  • implement-spec：把 tickets 当任务图，按 frontier 并行跑实现子代理，全部落到一个 integration branch。
  • retro：复盘这次会话，改进 agent 的工作环境而不是代码——导航指针、自动检查、评审标准。
为什么这三个一起毕业 它们解决的是同一个焦虑：agent 干得越来越快，但“收尾”还全靠人。合并、写 PR 说明、把这次踩的坑变成下次的护栏——恰恰是 vibe coding 最缺、而工程化最需要的部分。

03重点 ① pr

/pr

PR 描述该长什么样

model-invoked · agent 会自动用 1.3.0 毕业 只管 body，不开 PR

它是格式参考，不是工作流。不推分支、不开 PR、不决定改什么——只规定 agent 在写 PR body 时该用什么形状。

核心判断：默认的 PR body 是用散文描述 diff，这个技能要求用“能说清重点的最小可视化视图”。审阅者手上已经有 diff 了，body 的作用是让他读 diff 之前先看到 diff 的形状。

模板：三段，顺序固定

## Summary

<diagram, diff-sketch, or tree>

## Evidence

- **Before:** <screenshot/output/failing test run>
  **After:** <screenshot/output/passing test run>

## Merge Danger

**Door:** <one-way or two-way>

**Blast Radius:** <one-word description>

Summary — 六种视图，只挑一个或几个

伪代码（逻辑/算法）、调用树（运行控制流）、组件树（UI 结构 + 状态/模块边界）、浅文件树（职责划分/大重构）、Mermaid（交互/数据流）、shaped diff（形状已存在、重点是“改了什么”）。

技能明确写了：可以用一个，可以用几个，很少会用到全部。挑最小的那个。每个视图放在它所支撑的那句短文字旁边。

Evidence — 必须是“前后”，不是“结论”

  • 截图（S 级）——仅当改动是视觉的、且环境能截图时。
  • 执行证据（A 级）——测试结果、console 输出；写清“哪个测试之前失败、现在通过”。
  • “测试全绿”本身不是证据，那是一个主张。无 UI 的改动（迁移、后台任务、重构）就用失败→通过的测试或变化的 console 输出。

Merge Danger — 这是全篇的领头概念

把“这次合并安全吗？”从一个直觉变成一条可以被反驳的主张：

  • one-way door（单向门）：走不回去——破坏性迁移、公开 API 移除、难以回滚的决策。
  • two-way door（双向门）：回滚很便宜，风险低。
  • Blast radius：错了会波及什么——布局位移、API 消费方、移动端适配。

它同时告诉审阅者该在哪里花人类注意力：双向门 + 小爆炸半径就快读，单向门慢慢读。

来历 Summary 里那套“最小可视化”思路借自 Dex Horthy 的 show-me（humanlayer/skills）。上游在技能里带了 CREDITS.md 署名——顺带一提，本机也装了那个 show-me。

已知的坑（官方文档自己列的）

最该警惕的一条 别盲信 agent 自己的门的判定。写代码的那个 agent 在给自己打分，所以它说“双向门、爆炸半径小”的时候最该怀疑。回滚一个 commit 撤销不了已经发出的邮件；一次已标注的灰度发布，在第一次写入新格式之后就不再是双向门了。

缓解办法两条：① 确保 agent 手上有 ticket 或 spec，不只是 diff；② 把“本仓库永远视为单向门的改动”（schema 迁移、对外发布、删除类操作）写在 agent 会读到的地方。
  • 不会打开 PR——implement 结束于提交到当前分支；implement-spec 是唯一的例外。
  • 不处理回流的 review 评论，也不在 PR 改动后自动刷新 body（大改之后要让 agent 重写）。
  • 不读仓库自带的 .github/pull_request_template.md。默认两边互相打架，得在仓库的 agent 文档里定优先级（比如把三段嵌进仓库模板）。
  • 输出是 Markdown，不是 HTML。Mermaid 在 GitHub/GitLab 能渲染，在终端里是生的。
用对了的样子 只看 Summary 的图就能明白改了什么，不用打开 diff；body 没有前言，直接从 Summary 开始；Evidence 有前有后；每个 PR 都写了门和爆炸半径，而且你确实在单向门那里放慢了速度。

04重点 ② implement-spec

/implement-spec

一次跑完整个 spec

user-invoked · 只能你打 1.3.0 毕业 任务图 · 并行 · integration branch

它把 tickets 读成任务图而不是清单。blocking 边决定什么能开始，于是任何时刻都有一批“所有前置都已落地”的 tickets 构成frontier，frontier 上的全部同时开跑。节奏由图的形状决定，而不是它们在 tracker 上的排列顺序。

和 implement 的区别（这是这个技能存在的理由）

implementimplement-spec
谁在调度你：一个 ticket 一个会话，中间 clear，自己记着哪些解除了阻塞一个编排会话
并行度一次一个frontier 上有多少跑多少（后台子代理）
你什么时候读每个 ticket 落地就能读最后统一评审 integration branch
适用小改动、没有真正的图一个 spec 里 5+ 张 ticket

九步流程（SKILL.md 的实际步骤）

  1. 读 spec 和 tickets，理解任务图。
  2. （可选）用探索子代理把代码库/外部文档的调研做完，笔记存到仓库外一个所有后续子代理都能读到的目录。
  3. 建 integration branch。若 tracker 以 PR 收尾或你要求，则在第 5 步首次合并之后开 draft PR（没有领先 commit 的分支开不了 PR）。
  4. 用实现子代理逐张建 ticket，各自一个 worktree、各自一个分支。每个实现者：确认 worktree 基于 integration branch → 调用 tdd 建 ticket → 报告完成前把 integration tip 合并进自己分支。
  5. 实现者完成后，用合并子代理把它的工作合进 integration branch。
  6. 若 frontier 因此变化，立刻再起一批实现子代理——这是并发拉满的关键。
  7. 全部完成后，调 code-review 审 integration branch，所有问题交给一个实现子代理修。
  8. 有 draft PR 就标 ready；否则按 tracker 的方式收尾每张 ticket，并报告 integration branch。
  9. 清理所有实现者 worktree。
两个关键设计 ① 沟通用 context pointer：spec、ticket、探索笔记、之前的 commit——而不是把摘要粘来粘去。子代理的 prompt 保持小，编排者的窗口留给任务图。
② 落地必须是 fast-forward：每个实现者在报完成前先把 integration tip 合进自己分支，所以合并进主线不会变成冲突解决。

前置条件（缺一个就不是它该干的事）

  • issue tracker：由 setup-matt-pocock-skills 配置；没配就停下让你跑它，而不是猜着用 gh。
  • tickets 必须带 blocking 边（照 to-tickets 的写法）。没有边就是平图，所有 ticket 一起开跑。
  • harness 要支持后台子代理 + 每个一个 git worktree。不支持的话，它只是“更慢的 implement”。
离线可用 目标是 integration branch，不再是 PR。只有 tracker 以 PR 收尾、或你明确要 PR 时才开。配本地 markdown tracker 可以完全离线跑完，停在分支上，tickets 按 tracker 的方式关闭。

已知的坑（文档里用户报的真实问题）

坑 1 · review / fix 循环跑几小时 code-review 是拿代码对着整个 spec比的，所以只有在所有 ticket 都落地之后跑才有意义。中途跑的话，每张没建的 ticket 都会被读成失败 → agent 去建它 → 又触发一轮 review。有用户报过一张五 ticket 的特性，“review 和 fix 循环花了大约四小时”。如果看到第二轮全面 review 开始，直接叫它只做针对性检查然后停。
坑 2 · 并行不等于不冲突 worktree 不消除冲突，只是把冲突推迟到合并时。两件“代码库不同部位”的 ticket 仍然共享消息目录、配置注册表或某个类型。真实案例：web 和 mobile 两张 ticket 把同一个字符串分别命名成 blockedSince 和 blockedOn。规避：让两张 frontier ticket 之间有 blocking 边（串行），或者在探索笔记里把要新增的名字钉死。
坑 3 · GitHub 的 blocked-by 是过期数据 GitHub 的 blocked-by 计数只在 blocker 关闭时下降，而 tickets 通常是 PR 合并时才关闭——也就是整轮结束的时候。tracker 适合给出起始图，不适合作为中途的依据。让编排者自己按“哪些已经合进 integration branch”算 frontier。
坑 4 · worktree 里的测试会静默跳过还报绿 worktree 只有 git 跟踪的内容。依赖 gitignore 的 fixture、本地数据库或凭证的测试，在那里会静默 skip 然后报绿。这类 ticket 让编排者在主 checkout 里验证。
另外：它的输出是“草稿”，由那次 review 补完——不是能直接发的东西。tdd 现在每个实现者都会跑，但没有 implement 那种“和你交互确认 seam”的步骤，所以 seam 要写进 spec 或 tickets。

05重点 ③ retro

/retro

复盘会话，改的是环境不是代码

user-invoked · 只能你打 1.3.0 毕业 只提议，不动手

它读这次会话自己的记录，找到 agent struggle 的那些时刻，然后按严重程度排序给出一份候选修复清单——改的是 agent 的工作环境，不是代码。

agent 交付的那个 bug、它花了二十次工具调用才找到的文件、评审漏掉的那条规则——retro 都不直接修。它问的是：仓库里是什么让这些事发生？什么样的检查、指针或标准能让它下次不发生？

七类候选，类别决定修复落在哪

会话里发生了什么用什么修
找文件/事实花了很久导航指针（从一个它已经会读的文件指出去）
犯了一个工具本可以抓住的错自动检查：lint 规则、类型、测试、pre-commit hook、CI job
评审漏掉一个判断类错误CODING_STANDARDS.md 里给评审 agent 的规则
AGENTS.md / CLAUDE.md 太长把其中的 steering 搬到标准或检查里
某次工具调用性价比极低简化那个工具，或换掉它
steering 文件里全是“改了等于没改”的行删掉这些 no-ops
agent 拿不到它需要的信息放宽访问：把 dev server 日志 tee 到文件、给只读访问
领头判断 · standards 属于评审者，不属于实现者 实现 agent 的上下文压力最大（要探索、写代码、调失败）；评审 agent 只拿到一个 diff，压力最小。所以一条新规则应该放在有余力执行它的地方——评审。
它永远不放进 AGENTS.md：那是每个会话都加载的，不管相不相关。

写任何规则之前先分类违规

  • 机械性违规（禁用 API、import 形状、文件位置规则）→ 一律做成确定性检查（仓库自己的 linter 里的自定义规则 / 新 pre-commit hook / 新 CI job，取最便宜的那个）。能写检查就不要写规则。
  • 判断类（跨文件一致性、“和周围风格一致”、任何护栏无法替代的东西）→ 才写进 CODING_STANDARDS.md。
  • 仓库完全没有护栏（没有 pre-commit hook，也没有跑 lint/typecheck/test 的 CI job）——这本身就是一条 finding，不是中性默认值。
它也会先读仓库自己的检查命令（package.json/构建工具的 lint/check、CI workflow），所以“一个已经存在但没接上或悄悄坏掉的检查”才是 finding，而不是重新发明一遍。技能还要求先加载 writing-for-agents 拿写作风格。

怎么用

  • 会话还“热”的时候跑最好（默认复盘当前会话），因为 struggle 还在上下文里。
  • 会话已经出了 smart zone？先 clear，然后把新的 /retro 指向 session logs 里的那一次。
  • 跑在“本来就难”的会话后面才有价值——顺利的会话没什么可教。
它的弱点（文档里写得相当诚实） ① 只会堆积，不会清理。 它能删 prose（no-ops、该搬走的 steering），但不审计上个月自己提议的 lint 规则/hook/CI——它只看一次会话，没法告诉你某条规则现在太吵或它背后的 bug 已经消失。规则得你自己 prune：一条经常在好代码上报警的规则，就是该删的信号。
② 单个会话为样本。 安静但昂贵的错误可能排在响亮但便宜的错误后面。
③ 最容易挨的批评：编通用建议。 有用户说“任务一旦完成，AI 就忘了 session 中段的 struggle，然后为了填满 retro 的分类发明通用建议”。技能的对策是：每条候选都必须来自会话自己的记录——任何指不回具体时刻的候选，直接丢掉。
④ 无 dry-run，不自动装 hook。 它只提议，直到你挑了一条才动手。这是刻意的：有用户被“自动 hook 拦住了好的改动”烫过。
用对了的样子 每条候选都能指回会话里某个具体时刻；重复犯的错变成了会失败的检查；你的 AGENTS.md 越来越短而不是越来越长；检查本来就有、只是没接上——那 finding 是“接上它”而不是“再建一个”。

06其他值得说的

流程与写法约定

  • grilling 被重写了——从“一次问一个问题，多问会让人晕”改成按轮次问完整个 frontier（先把所有前置已定的问题一次问完，每问都附推荐答案，等你答完再算下一轮 frontier）。另外加了确认门：没确认达成共识之前不许动手；并且把事实（自己查）和决策（必须问你）分开——旧写法在“技能内部跑 grilling”的场景下被读成了“决策也可以自己答”。（今天你正好亲眼看了新版行为。）
  • 全线扫掉 em-dash，每一句都是手改的（逗号/冒号/句号/括号/连接词），不是字符替换；CLAUDE.md 里写明不许再加回来。
  • user-invoked / model-invoked 的区分成为正式不变式：前者只能你打、用来编排；后者能被模型自动触发；前者只能调用后者。
  • ask-matt（路由器）同步更新：补上了 tdd、diagnosing-bugs（新增“东西坏了”入口）、domain-modeling/codebase-design（“底层词汇”）、grilling，以及三条 on-ramp 和 phase boundary 决策树（PHASE-BOUNDARIES.md）。
