00总览：一条 idea → ship 的主流程

这批 skill 不是零散工具，而是一套有明确设计意图的工程流水线。ask-matt 技能（技能路由器）把整张地图讲得很清楚：

/grill-with-docs→ /to-spec→ /to-tickets→ /implement-spec→ /pr→ /retro 拷问出想法 → 固化为 spec → 拆成带阻塞关系的 ticket → 并行实现 → PR 描述 → 复盘环境

本次更新的三个主角，恰好覆盖了主流程的后三段

  • /pr — PR 正文的写作模板：最小可视化 + 前后证据 + 合并风险评级。model-invoked
  • /implement-spec — 把整个 spec 一次性实现：ticket 视为任务图，多 implementer 子代理并行推进。user-invoked
  • /retro — 对 coding session 做复盘，改进对象是 agent 的环境而非代码本身。user-invoked

注意 /pr 是 model-invoked（agent 写 PR 时自动触发），另外两个是 slash command 手动触发。这是有意的分层：写 PR 是高频机械动作交给模型，编排和复盘是人的决策。

01/pr — PR 正文模板NEW

写 PR 描述的技能。最大的特色是强制可视化：Summary 不许写成大段散文，必须从一组固定的「图示菜单」里挑最小够用的一种。致谢文件（CREDITS.md）表明它源自 Dex Horthy（HumanLayer）的 show-me 技能，内容几乎逐字移植，只是把目标从「现场讲解」改成了「描述一个 diff」。

PR 正文三段式模板

## Summary <diagram, diff-sketch, or tree> ← 图示，不是散文 ## Evidence - Before: <截图/输出/失败的测试> - After: <截图/输出/通过的测试> ← 前后对照证据 ## Merge Danger Door: <one-way | two-way> ← 是否可回滚 Blast Radius: <一个词> ← 影响范围

Summary 的「图示菜单」—— 六种可选表达

形式适用场景示例
pseudocode逻辑 / 算法on(save) if unchanged → return cached
call tree运行时控制流submitForm → createSession → persistPrompt
component treeUI 结构 / 状态边界<SessionPage> → <SessionToolbar>
file tree文件职责 / 大重构src/ ├── commands/ ├── sessions/
Mermaid组件交互 / 数据流sequenceDiagram
diff关键变更点（形状对应主题）+ <RunSkillButton />

原则：每张图紧挨它支持的短文字；只保留回答当前问题所需的调用、文件、状态和边界；「不太可能全用上，别压垮读者」。

Evidence 与 Merge Danger 的分级

  • Evidence 分级：截图 S-tier（改了视觉就上截图）；可执行证据 A-tier（测试结果 / 控制台输出，用伪代码展示「之前失败、现在通过」的确切测试）。
  • Door：单向门 vs 双向门 —— 廉价可回滚的 PR 风险低；涉及破坏性操作或难以逆转决策的是单向门。这是典型的贝索斯「one-way / two-way door」决策框架。
  • Blast Radius：一个词概括潜在影响范围 —— 布局偏移、下游破坏、移动端适配等所有可能性。
点评：它把「PR 描述怎么写」从自由发挥变成格式约束下的工程判断。reviewer 第一眼看到的是图和风险评级，而不是需要自己从散文里提炼的意图 —— 显著降低 review 成本。

02/implement-spec — 整个 spec 一次实现NEW

对应旧流程里「逐个 ticket 手动 /implement + 每张 ticket 之间 /clear」的替代方案：当整个 spec 已经通过 /to-spec / /to-tickets 拆解完毕，它把实现工作升级为子代理编排，一次跑完全部 ticket。

核心抽象：tickets 是任务图（task graph），不是步骤列表

每张 ticket 声明自己的 blocking edges（阻塞关系）。任意时刻都存在一个frontier：所有前置已完成的、现在就能开工的 ticket 集合。编排的本质就是不断消化 frontier 并随合并推进扩展它。

spec + tickets→ integration branch→ frontier 并行开工→ merger 逐个合并→ code-review→ PR ready

九步流程中的关键设计

  • 通信靠 context pointers，不靠复制：子代理之间主要传递指向 spec、ticket、research notes、历史 commit 的指针，sparse communication——避免信息重复膨胀。
  • exploration subagent（可选）：预先把 ticket 需要的代码库 / 外部文档调研做成 markdown 笔记，存到仓库外的目录供所有后续子代理共用，让 implementer 专注写代码。
  • 每个 implementer 独立 worktree + 独立分支，开工前确认基于 integration branch（不对则 reset 重定位）；内部驱动 /tdd 逐个红绿循环；完工前先把 integration branch tip 合进自己分支再报告。
  • 合并由专门的 merger subagent 负责，每次合并可能解锁新的 frontier ticket → 立即派出更多 implementer，最大化并发。
  • 首个合并后即开 draft PR（空分支开不了 PR），标记为关闭该 spec 及全部 ticket。
  • 收官：全部 ticket 完成后，对 integration branch 跑一次 /code-review，发现的问题由单个 implementer 子代理统一修复；然后 draft PR 转 ready，清理所有 worktree。

与 /implement 的分工

/implement（逐张票）/implement-spec（整包编排）
驱动方式人在主会话逐张驱动，票间 /clear一次调用，子代理自动编排
并发串行frontier 内所有就绪 ticket 并行
隔离主会话直接改每票独立 worktree + 分支
code-review每张票各跑一次整个 integration branch 跑一次
适用想亲自控制每一步「宁可做编排者，不想逐票驾驶」
点评：这是把「人类逐票驾驶」升级为「agent 当工头」。任务图 + frontier + 独立 worktree + 指针通信，四个约束合起来解决了多代理并行的经典问题——上下文重复、分支冲突、无序抢票。

03/retro — Session 复盘NEW

对一次 coding session 做回顾，但产出不是改进代码，而是改进 agent 的工作环境——下次跑得更好。它明确写出「实现 vs 审查」的两阶段认知：实现代理上下文压力最大，审查代理拿到 diff 压力最小，所以编码标准应该由审查方执行，而不是塞进实现方的 AGENTS.md。

七个检查类别（按严重度向用户提交建议）

类别找什么触发信号
Navigation文件间的隐性依赖，需要加导航指针找某个信息花了很久
Automated checks已存在却没接线 / 静默坏掉的检查；没有任何 guardrail 的仓库本身就是 findingagent 犯了机器能拦的错误
Coding standards机械类违规→确定性检查（linter 规则 / pre-commit / CI，默认造检查而不是写规则）；判断类才进 CODING_STANDARDS.md（跨文件一致性、「符合周边风格」）reviewer 漏掉了错误
Global AGENTS.md该下放到 coding standards 或自动化检查的指令AGENTS.md 过大（仓库级或全局）
Tool economy昂贵且可精简的工具调用、token 低效的工具出现了昂贵调用
No-ops不改变 agent 行为的死指令steering 文件臃肿
Information accesstee dev server 日志、第三方服务只读权限等关键信息 agent 拿不到

流程与文件职责

  • 先调 /writing-for-agents 拿写作风格，再读 session 日志（用户没指定就复盘当前会话），按严重度排序呈现改进候选。
  • AGENTS.md/CLAUDE.md：进每个 agent 的上下文，必须极省，通常只放导航指针。
  • CODING_STANDARDS.md：审查时读、实现时不读；超过 1000 行要加指向 docs 的导航指针。
  • 先读仓库自己的 check 命令（package.json 的 lint/check 脚本、CI workflow），已存在但没接线的检查本身就是 finding，而不是重新发明一个。
点评：这条 skill 是整套体系的「飞轮」。别的 skill 改代码，/retro 改环境：机械错误沉淀成确定性检查、判断类错误沉淀成标准、死指令被清除——每次构建后环境变好一点，形成复利。配合 /diagnosing-bugs 的说明（修完 bug 在同一 session 跑 retro 问「什么本可预防它」），闭环更完整。

04其他值得说的更新

除三个主角外，这一批里还有不少成形的设计值得留意：

/wayfinder — 大雾工程的决策地图NEW-ish

针对「一个 session 装不下、路线完全看不见」的超大工程（绿地项目 / 超大 feature）：在 issue tracker 上铺一张决策 ticket 的共享地图，逐张解决，产出决策而非交付物，直到路线清晰。地图清空后交接而不施工——在 /to-spec 汇入主流程。文档明确警告：直接从地图跳 /implement 会丢掉关联决策。

/to-tickets — tracer-bullet 拆票

把 spec 拆成「曳光弹」ticket，每张声明 blocking edges：本地 tracker 是 .scratch/<feature>/issues/ 一票一文件、阻塞关系写在文本里；真实 tracker（GitHub/GitLab）则用原生 blocking link。这正是 /implement-spec 任务图的物料来源。

/triage — 五角色状态机

只 triage 不是你自己创建的 issue（bug 报告、外部 PR、原始 feature 请求）；/to-tickets 产出的票已经 agent-ready，不再过 triage。五角色：needs-triage → needs-info / ready-for-agent / ready-for-human / wontfix。

写作与沟通类

06总结

三个新技能补齐了主流程的「出口」和「回路」

/pr 把 review 成本压到最低：图示代替散文，证据前后对照，风险一句话定级。

/implement-spec 把人从逐票驾驶解放成编排者：任务图 + frontier 并发 + 独立 worktree + 指针通信。

/retro 是唯一的复利来源：不修代码，修环境——机械错误变确定性检查，判断类错误变标准，环境每次构建后更好一点。

合起来看，这批更新让 idea → ship 变成了完整闭环：grill 出想法 → spec → tickets → 并行实现 → 可视化 PR → 复盘环境 → 下次更好。
